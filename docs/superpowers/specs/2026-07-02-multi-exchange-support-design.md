# Поддержка альтернативных бирж (уход Binance из ЕС)

**Дата:** 2026-07-02 (обновлено 2026-07-05)
**Ветка:** не создана (draft)
**Статус:** design approved (Approach A, аддитивная поддержка нескольких бирж + unified-аккаунты)

## Проблема

Binance не получил лицензию MiCA к дедлайну 30.06.2026 (отозвал заявку в Греции 24.06.2026)
и с 01.07.2026 приостановил новые заказы, депозиты и регистрации для резидентов ЕС.
Binance заявляет, что намерен получить лицензию через Францию и вернуться, но сроков нет.
Из ~3000+ крипто-компаний в ЕС полную MiCA-авторизацию получили только ~210 (~7%),
включая **Coinbase, Kraken, OKX, Crypto.com**.

Источники: [CoinDesk](https://www.coindesk.com/policy/2026/06/26/binance-tells-eu-users-it-will-no-longer-provide-services-after-failing-to-secure-mica-license),
[Euronews](https://www.euronews.com/business/2026/06/25/binance-to-halt-crypto-services-across-eu-countries-after-failing-to-secure-mica-approval)

Приложению нужна возможность торговать через хотя бы одну MiCA-лицензированную биржу.

## Цель

1. Добавить поддержку нескольких (2-3) популярных бирж аддитивно — не заменяя
   Binance, а расширяя набор поддерживаемых площадок.
2. Заложить архитектуру так, чтобы следующая биржа (или возврат Binance через
   Францию) добавлялась как ещё один адаптер, а не повторным рефакторингом.
3. Пользователь может привязать свой аккаунт к нескольким учётным записям на
   разных биржах одновременно и переключаться между ними.
4. Дать единый (unified) вид учёта — балансы/позиции/ордера по всем привязанным
   биржевым аккаунтам пользователя в одном месте, а не по одной бирже за раз.
5. Не потерять существующую функциональность (Naive/Grid/DCA стратегии, risk management,
   position tracking) при миграции.

## Текущая связанность с Binance (факты, по итогам исследования кода)

Абстракции биржи в коде сегодня **нет**. Binance зашит по имени модуля, по
compile-time конфиг-ключу `:binance`, и — важнее всего — сырой JSON-формат Binance
(однобуквенные ключи) протёк в ~10 модулей `trading_engine`.

| Область | Состояние |
|---|---|
| `DataCollector.BinanceClient` | Литерально Binance: `/api/v3/*`, `X-MBX-APIKEY`, HMAC-SHA256 (проверено лично: `binance_client.ex:16,646-652`). Поведения (`behaviour`) нет. **Уточнение после личной проверки:** вызывается по полному имени модуля не из 4, а из **~9 файлов, 20+ мест** — `trading_engine` (`Trader`, `OrderManager`, `SymbolInfo`, `Credentials`, `strategies/dca.ex`) **и** `dashboard_web` LiveViews (`orders_live.ex`, `history_live.ex`, `portfolio_live.ex`, `trading_live.ex` — балансы, тикеры, klines, depth, создание/отмена ордеров, история). Первоначальный отчёт research-агента не заметил слой `dashboard_web` — учтено ниже в плане (не всё покрывается первым этапом). |
| `DataCollector.BinanceWebSocket` + `TickerStream`/`KlineStream`/`DepthStream` | Литерально Binance: хардкод `wss://stream.binance.com:9443`, диспатч по полю `"e"` (`executionReport`, `24hrTicker`, ...). |
| `RateLimiter` | Алгоритм переиспользуемый, но лимит `1200 req/min` — Binance-специфичный параметр. |
| `CircuitBreaker` | Полностью переиспользуемый (принимает `circuit_name`). |
| `trading_engine` (стратегии, `Trader`, `PositionTracker`, conditions) | Поведение `Strategy` (`init/on_tick/on_execution`) само по себе биржа-агностично, но стратегии читают сырые ключи Binance (`"c"`, `"L"`, `"X"`, `"i"`, ...) напрямую в ~10 модулях. |
| `shared_data`: `api_credentials`, `accounts`, `orders` | Нет поля `exchange`. `orders.order_id` уникален сам по себе (коллизия между биржами). `orders` валидирует Binance-enum'ы типов/статусов. `accounts.binance_account_id` — Binance-именованная колонка. Хранилище кредов — 2 поля (api_key/secret_key), не хватает третьего секрета (passphrase) для OKX/Coinbase. |
| PubSub | Имена топиков (`market:#{symbol}`, `order_updates`, `balance_updates`) сами по себе не Binance-специфичны, но полезная нагрузка — сырые Binance-карты, и нет неймспейса по бирже (`market:BTCUSDT` от двух бирж пересечётся). |
| Config | Base URL читается через `Application.compile_env(:binance, :end_point, ...)` — **compile-time**, нельзя переключить в рантайме. WS-хосты — литералы в коде, не конфиг. |

**Вывод:** «быстрый» вариант (переписать `BinanceClient` в `KrakenClient` один в один,
не трогая остальное) всё равно требует правок в тех же ~10 модулях, что и «правильный»
адаптерный вариант — потому что связанность уже размазана по коду. Экономия от
«быстрого» пути минимальна, а результат хуже (следующая биржа — снова полный рефакторинг).

## Рассмотренные подходы

**A. Адаптерный retrofit с канонической моделью данных (рекомендуется)**
Поведение `ExchangeClient` (`create_order/cancel_order/get_open_orders/get_account/
get_exchange_info/get_klines`), канонический struct для market data / execution report,
собираемый на уровне WS/stream-слоя. `BinanceClient` становится первым адаптером,
для новой биржи пишется второй. Стратегии/трекеры переводятся на канонический struct.
*Плюсы:* следующая биржа — это адаптер + маппинг символов, без переписывания
стратегий. *Минусы:* больше работы на старте (нормализация payload — самое
широкое по площади изменение).

**B. Прямая замена (`BinanceClient` → `KrakenClient`), без слоя абстракции**
Минимальные архитектурные изменения, максимально быстрый выход в продакшн.
*Минусы:* как показал разбор кода, объём правок почти совпадает с (A) — те же ~10
модулей всё равно трогаются, потому что raw-ключи читаются напрямую. При этом
получаем худшую архитектуру и придётся переделывать это же при следующей смене биржи.
Экономии по факту нет, только техдолг.

**C. Инкрементальная миграция (поведение + канонический struct только для новых
модулей, `BinanceClient` остаётся как есть до тех пор, пока не тронут руками)**
Ниже стартовые затраты, но два параллельных формата данных одновременно (сырой
Binance + канонический) усложняют стратегии и тестирование на переходный период.
Может быть шагом к (A), но не отдельной конечной архитектурой.

**Рекомендация: подход A**, поэтапно (см. ниже) — чтобы торговля не простаивала
всё время миграции, и потому что B не даёт реальной экономии при этой связанности.

## Целевые биржи (подтверждено пользователем: 2-3 самых популярных)

MiCA-лицензированы: Coinbase, Kraken, OKX, Crypto.com.

**Выбор: Kraken, OKX, Coinbase** — три адаптера первой волны.

- **Kraken** — первая биржа с полной MiCA-лицензией (Central Bank of Ireland,
  июнь 2025), также держит MiFID/EMI лицензии. REST/WebSocket/FIX API стек —
  по функциональности ближе всего к тому, что сейчас использует приложение
  (гранулярные типы ордеров, потоковые данные), что важно для Grid/DCA/Naive
  стратегий. Приоритет №1 — первый адаптер после Binance.
- **OKX** — MiCA-лицензирована, одна из крупнейших бирж по объёму/ликвидности;
  хороший источник исполнения для стратегий, чувствительных к проскальзыванию.
  Зрелость retail/algo API для этого конкретного кейса будет подтверждена
  на этапе research перед реализацией адаптера.
- **Coinbase** — MiCA-лицензирована, самая широкая узнаваемость/пользовательская
  база в ЕС; API больше рассчитан на guided/простые сценарии, поэтому идёт
  третьим — покрытие популярности важнее гранулярности для части пользователей.

Все три подключаются через одно и то же `ExchangeClient` behaviour (см. ниже) —
порядок реализации: Kraken → OKX → Coinbase, каждый адаптер отдельным этапом
с собственным набором contract-тестов.

`BinanceClient`-адаптер не удаляется, а остаётся дормантным (и рабочим, если
Binance разрешат в конкретной юрисдикции ЕС / когда вернутся через Францию) —
в адаптерной архитектуре это просто ещё один вариант в списке, без отдельного
рефакторинга.

## Архитектура (подход A)

### 1. Канонический слой данных
Новые структуры (например, `TradingEngine.MarketTick`, `TradingEngine.ExecutionReport`)
с семантическими полями (`price`, `quantity`, `side`, `status`, ...) вместо
однобуквенных Binance-ключей. Собираются в WS/stream-слое каждого адаптера перед
броадкастом в PubSub — стратегии, `Trader`, трекеры, conditions читают только
канонический struct.

*Это самое широкое по площади изменение (~10 модулей trading_engine), но
не зависит от REST-адаптера и схемы БД — можно делать первым и независимо.*

### 2. `ExchangeClient` behaviour + REST-адаптеры
```elixir
@callback create_order(Types.account_id(), Types.order_params()) :: Types.result(Types.order())
@callback cancel_order(Types.account_id(), Types.order_id()) :: Types.result(:ok)
@callback get_open_orders(Types.account_id(), symbol :: String.t()) :: Types.result([Types.order()])
@callback get_account(Types.account_id()) :: Types.result(Types.account())
@callback get_exchange_info(symbol :: String.t()) :: Types.result(map())
@callback get_klines(symbol :: String.t(), interval :: String.t()) :: Types.result([map()])
```
`BinanceClient` реализует behaviour как есть (адаптер #1, без изменений тела функций —
только `@behaviour` аннотация, сигнатуры уже совпадают). Новый `KrakenClient` — адаптер #2.

**Два эшелона рерута, разного риска:**
- `Trader`/`OrderManager`/`Credentials.test_credential` (trading_engine + shared_data,
  ~7 мест) — уже имеют доступ к `exchange` через `account`/`credential` в своём
  контексте, переключаются на диспатч через `ExchangeRegistry` в рамках **первого
  этапа** (см. "Порядок внедрения").
- `dashboard_web` LiveViews (`orders_live.ex`, `history_live.ex`, `portfolio_live.ex`,
  `trading_live.ex`, ~20 мест) — сейчас работают, потому что других бирж ещё нет;
  **не трогаются в первом этапе**, рерут откладывается до этапа с первым реальным
  вторым адаптером (Kraken), потому что до этого момента правки там ничего не меняют
  функционально, а трогать 20 мест без реальной проверки на живой второй бирже —
  не оправданный риск. `SymbolInfo` (не exchange-aware, единственный вызов из
  `conditional_chain.ex`) откладывается туда же по той же причине.

### 3. Схема БД (уточнено после личной проверки схем и миграций)

- `api_credentials`: добавить `exchange` (`:string`, `not null`, `default: "binance"`,
  `validate_inclusion` — список расширяется по мере добавления адаптеров). **Только
  здесь** нужен дискриминатор — `Account belongs_to :api_credential` 1:1, так что
  `account.api_credential.exchange` уже достаточно для резолва адаптера; дублировать
  поле на `accounts` не нужно (YAGNI). `passphrase` (опционально, нужно
  OKX/Coinbase) добавляется в план соответствующего адаптера, не сейчас — Kraken
  им не требуется.
- `accounts.binance_account_id` — переименование не требуется для мульти-биржевости
  (это просто пользовательская метка счёта на бирже), оставляем как есть, чтобы не
  расширять diff; можно переименовать отдельным косметическим PR.
- `orders`: **не добавляем `exchange`** — уникальность вместо `unique_index(:orders,
  [:order_id])` меняем на `unique_index(:orders, [:account_id, :order_id])`, так как
  `orders.account_id` уже однозначно определяет биржу через `account.api_credential`.
  Это также чинит существующий скрытый баг: `order_id` сегодня уникален глобально
  даже в рамках одного Binance — двух разных аккаунтов с одинаковым `order_id`
  быть не должно, но ничего в схеме сегодня этого не гарантирует правильно
  (unique per exchange-account, не per app). Enum-валидацию типов/статусов пока не
  трогаем — актуально при реализации адаптера, чей набор типов ордеров отличается.
- Формат символа: канонический внутренний формат и маппинг на биржа-специфичный —
  переносится в план Kraken-адаптера (Plan 1 не переводит ни одного реального
  запроса на не-Binance формат, обсуждать маппинг раньше времени — YAGNI).

### 4. Конфиг
Переезд с compile-time `Application.compile_env(:binance, ...)` на runtime,
конфиг с ключом по бирже (`config :data_collector, exchanges: [binance: [...], kraken: [...]]`),
WS-хосты — тоже в конфиг, не литералы.

### 5. PubSub
Топики неймспейсятся по бирже: `market:#{exchange}:#{symbol}` вместо
`market:#{symbol}`, аналогично для `order_updates`/`balance_updates`, либо
эти данные остаются per-account (уже подразумевает единственную биржу на аккаунт).

### 6. Мульти-аккаунтность и unified-вид (новое, по итогам обсуждения)

**Хорошая новость:** модель `User` → `Account` (1:N) → `ApiCredential` уже
существует и уже поддерживает несколько аккаунтов на пользователя —
`SharedData.Accounts.list_user_accounts/1` и `list_user_api_credentials/1`
работают без ограничения "один аккаунт на пользователя". Сегодня каждый такой
аккаунт неявно означает Binance. Значит "привязать аккаунт к нескольким
учётным системам и переключаться между ними" в основном уже есть на уровне
данных — не хватает только:

1. Поля `exchange` на `Account`/`ApiCredential` (уже запланировано в п.3 —
   "Схема БД"), чтобы каждый `Account` знал, к какой бирже он относится.
2. `TradingEngine.Trader` (уже один GenServer на аккаунт через
   `TraderRegistry`) при старте резолвит адаптер по `account.exchange` —
   архитектура процессов не меняется, просто параметризуется биржей.
3. **Новый слой — unified portfolio view**: агрегирующий запрос/LiveView в
   `dashboard_web`, который берёт все аккаунты пользователя (через все биржи)
   и показывает объединённые балансы/позиции/историю ордеров в одном месте.
   Требует:
   - канонический символ/актив для сопоставления одного и того же актива
     между биржами (например, "BTC" как база, а не Binance "BTCUSDT" или
     Kraken-специфичный формат пары) — использует ту же нормализацию, что и
     каноническая market-data структура (п.1);
   - решить, показывать ли балансы в единой валюте (агрегированная стоимость
     портфеля) — если да, нужен курс конвертации (может уже быть в
     `MarketData`/тикерах, либо отдельный источник цен);
   - UI для переключения "контекста" (один аккаунт/биржа) отдельно от
     unified-обзора (все аккаунты сразу) — вероятно расширение существующего
     аккаунт-селектора в `dashboard_web`, а не новый механизм с нуля.

Процессная модель "один Trader на аккаунт" остаётся: unified-вид — это
слой чтения/агрегации поверх существующих данных, не альтернативная
архитектура треугольника Trader/Strategy/Exchange.

## Переиспользуется без изменений
`CircuitBreaker`, `RateLimiter` (алгоритм — лимит-константы становятся
per-exchange конфигом), `RiskManager`, форма поведения `Strategy`, большая часть
`Trade`/`Balance` схем, PubSub-инфраструктура как таковая.

## Порядок внедрения (чтобы не простаивать всё время миграции)

1. Канонический market-data/execution struct на уровне stream-слоя (снимает самую
   широкую связанность в `trading_engine`, не блокируется остальным).
2. `ExchangeClient` behaviour + перевод 4 точек вызова на диспатч через него
   (механическая правка, `BinanceClient` продолжает работать как единственный
   адаптер на этом шаге).
3. Схема БД: `exchange`-дискриминатор на `api_credentials`/`accounts`/`orders`
   + фикс уникальности `orders` на `(exchange, order_id)` — должно попасть в БД
   до первой записи от второй биржи.
4. Runtime-конфиг вместо compile-time.
5. Адаптер #1 — **Kraken**: REST + WS, маппинг символов/типов ордеров,
   contract-тесты по `ExchangeClient` behaviour, testnet.
6. Unified portfolio view в `dashboard_web` — на этом шаге уже есть 2 биржи
   (Binance + Kraken), достаточно для первой версии агрегированного вида;
   расширение account-селектора на "все аккаунты" режим.
7. Адаптер #2 — **OKX** (REST + WS, тот же контракт).
8. Адаптер #3 — **Coinbase** (REST + WS, тот же контракт).
9. E2E тест на testnet каждой новой биржи по мере готовности адаптера (не
   откладывается до конца — каждый адаптер тестируется в своём шаге).

## Тестирование

- Unit-тесты на канонический struct: конвертация из сырого payload каждой биржи
  в канонический формат (табличные тесты — один и тот же canonical output из
  разных raw-фикстур).
- `ExchangeClient` behaviour — общий набор contract-тестов, прогоняемый против
  каждого адаптера (аналогично тому, как сейчас `Strategy` behaviour тестируется
  через существующие стратегии).
- Order-schema: тест на коллизию `order_id` между двумя биржами (должен пройти
  после фикса уникальности).
- Новый адаптер тестируется на testnet выбранной биржи по аналогии с текущим
  `BINANCE_BASE_URL=https://testnet.binance.vision`.

## Решено по итогам обсуждения

1. ~~Какая биржа первая?~~ → **Kraken, OKX, Coinbase**, в этом порядке (см. выше).
2. ~~Держим ли `BinanceClient` дормантным?~~ → **Да**, остаётся как один из
   адаптеров, не удаляется.
3. ~~Один аккаунт = одна биржа?~~ → **Да, один `Account` = одна биржа** (как и
   сейчас), но **пользователь может иметь несколько `Account` на разных
   биржах** и получает unified-вид поверх всех них (см. "6. Мульти-аккаунтность").

## Открытые вопросы

1. Нужна ли миграция существующих открытых позиций/ордеров с Binance, или это
   голый cutover (закрыть на Binance вручную, открывать новые позиции уже на
   новой бирже)?
2. Показывать ли объединённую стоимость портфеля в единой валюте (требует
   курсов конвертации между активами/биржами), или unified-вид ограничивается
   построчным списком балансов/позиций без агрегации в одну сумму на первой
   итерации?
3. Порядок реализации адаптеров (Kraken → OKX → Coinbase) — фиксированный,
   или можно менять местами OKX/Coinbase в зависимости от того, что быстрее
   даст доступ к API/документации на этапе research?

## Риски

- Нормализация payload — самое трудоёмкое и самое рискованное по площади
  изменение (10+ модулей, вероятность регрессий в стратегиях).
- Символьный формат разных бирж отличается — нужен явный маппинг-слой,
  иначе тихие ошибки в расчёте quantity/price (например, разные lot-size /
  tick-size фильтры, увидено в `SymbolInfo` для Binance). С тремя новыми
  биржами это три отдельных маппинга, а не один.
- Три адаптера вместо одного — три разных auth-схемы (Kraken: API
  key + private key подпись; OKX/Coinbase: нужен третий секрет —
  passphrase), три набора rate-limit правил, три WS-протокола
  (переподключение/heartbeat у каждой биржи свои). Каждый адаптер
  требует отдельного research-захода перед реализацией — закладывать
  время на это в implementation plan, не считать адаптеры №2/№3
  "по аналогии бесплатными".
- Unified-вид с конвертацией в единую валюту (если решат делать — см.
  открытый вопрос №2) добавляет зависимость от курсов между активами,
  которых сейчас в системе может не быть в нужном виде.
